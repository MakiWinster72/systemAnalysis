# 原型方法：迭代式需求定义技术

## 定义

原型方法（Prototype Method）是一种与[[summaries/11.6.1需求定义的方法|严格定义方法]]截然不同的需求定义技术。它采用迭代循环的[[concepts/软件开发方式|开发方式]]，强调开发人员与用户的通力合作，通过构建原型系统来逐步明确和完善需求。

## 核心理念

原型方法的本质是**承认需求的不确定性**。它认为：

> 并非所有的需求都能在系统开发前被准确地说明。

用户虽然能描述最终系统的目标和大致功能，但对细节问题往往难以十分清楚。系统开发过程无论对开发人员还是用户，都是一个学习和实践的过程。

## 工作流程

1. **初始原型构建**：从满足用户基本需求的原型系统开始
2. **用户评审**：用户对原型进行研究、实践和评价
3. **需求迭代**：根据用户反馈提出更好的要求
4. **系统完善**：开发人员根据要求不断改进系统
5. **循环往复**：重复以上过程直至需求明确

```
┌─────────────┐    用户评审    ┌─────────────┐
│  构建原型   │ ───────────→  │  需求反馈   │
└─────────────┘               └─────────────┘
       ↑                              │
       └────────────── 迭代完善 ──────┘
```

## 关键特征

| 特征 | 说明 |
|------|------|
| 迭代性 | 循环往复、逐步逼近 |
| 协作性 | 开发人员与用户紧密合作 |
| 渐进性 | 从基本需求到完善需求 |
| 实践性 | 通过原型实例而非文档进行沟通 |

## 优势

- **降低需求风险**：通过早期原型验证，降低理解偏差
- **促进沟通**：用实际可操作的原型替代抽象文档描述
- **适应变化**：允许需求在开发过程中演进
- **用户参与**：用户通过实践参与需求定义，而非被动接受

## 与严格定义法的对比

| 维度 | 严格定义法 | 原型方法 |
|------|-----------|----------|
| 假设基础 | 需求可预先完全定义 | 需求需在实践中逐步明确 |
| 沟通媒介 | 静态文档、图表 | 可运行的原型系统 |
| 开发模式 | 线性、一次性 | 迭代、循环 |
| 用户角色 | 需求提供者 | 积极参与者 |
| 适用场景 | 需求明确的小型系统 | 需求不确定的复杂系统 |
