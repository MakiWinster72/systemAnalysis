# 软件架构质量属性

软件架构质量属性是描述软件系统在特定条件下行为特性的非功能需求，用于衡量系统满足利益相关者期望的程度。与功能性需求描述系统"做什么"不同，质量属性描述系统"做得如何"——即系统的行为特性在各种场景下的表现。质量属性是架构设计的核心关注点，直接影响系统的可靠性、效率和用户满意度。

## 质量属性场景的六要素

为了精确描述质量属性，架构师采用[[summaries/12.6.3质量属性场景描述|质量属性场景]]（Quality Attribute Scenario）作为标准化的描述手段。每个质量属性场景包含以下六个要素：

| 要素 | 说明 |
|------|------|
| **刺激源** | 生成刺激的实体（人、计算机系统或其他刺激器） |
| **刺激** | 到达系统时需要考虑的条件 |
| **环境** | 刺激发生时的系统状态（正常/过载等） |
| **制品** | 被激励的系统或系统组件 |
| **响应** | 激励到达后系统采取的行动 |
| **响应度量** | 用于测试和验证响应的可量化指标 |

## 六类核心质量属性

### 1. 可用性（Availability）

可用性关注系统正常运行的能力，即系统在面对各种故障和异常情况时能够继续保持可用状态。关注的方面包括：

- 故障发生的频率
- 故障发生时的系统行为
- 允许的停机时间
- 安全故障的时机
- 故障预防措施
- 故障通知机制

**实现策略**：
- **数据冗余**：将数据复制到多个节点或存储设备中，保证数据的可靠性和可用性。当一个节点或设备发生故障时，系统可以自动切换到其他节点或设备上继续工作
- **自动故障转移**：节点或设备发生故障时自动切换到备用节点继续工作，可通过ZooKeeper、Keepalived、Pacemaker等工具实现
- **负载均衡**：将工作任务分配到多个节点或计算单元上，平衡每个节点的负载，可通过Haproxy、Nginx、LVS等工具实现

**响应度量**：可用时间间隔、系统可用率、降级模式运行时间、故障修复时间

### 2. 可修改性（Modifiability）

可修改性关注系统在改变功能或质量属性时需要付出的成本和难度。修改可能发生在：

- 系统设计时
- 编译时
- 构建时
- 运行时

**响应度量**：人力成本、修改所需时间、资金成本

### 3. 性能（Performance）

性能关注系统的响应速度，通过以下指标客观评价：

- 效率
- 响应时间
- 吞吐量
- 负载能力

**实现策略**：
- **分布式存储**：通过将数据分散存储在多个节点上，提高系统的并行度和计算效率
- **并行处理**：将任务分成多个子任务，在多个计算单元上同时执行，充分利用计算资源快速完成任务
- **内存计算**：将数据存储在内存中进行计算，避免磁盘I/O和网络传输带来的延迟，大大提高计算效率，在处理大数据集时尤其有效

**响应度量**：等待时间、期限、吞吐量、抖动率、缺失率、数据丢失率

### 4. 可测试性（Testability）

可测试性关注系统测试的效率，包括：

- 发现缺陷的难易程度
- 测试环境的准备
- 测试覆盖程度

**响应度量**：语句覆盖率、缺陷发现概率、测试执行时间、测试环境准备时间

### 5. 易用性（Usability）

易用性关注用户使用系统的容易程度，包括：

- 学习曲线
- 操作效率
- 错误容忍度
- 满意度

**响应度量**：任务完成时间、错误数量、用户满意度、学习成功率

### 6. 安全性（Security）

安全性关注系统在向合法用户提供服务的同时，阻止非授权使用的能力：

- 身份认证与授权
- 数据保护
- 访问控制
- 审计追踪

**响应度量**：攻击检测率、身份确定可能性、拒绝服务抵抗率、数据恢复时间

## 系统稳定性

稳定性是系统能够长时间运行和高负载情况下保持稳定和可靠的能力，是质量属性在实际系统运维中的综合体现。实现稳定性的关键策略包括：

- **监控和预警**：对系统的各个组件进行实时监控，在出现异常情况时能够及时发出警报，以便及时处理
- **性能调优**：通过优化系统的各个组件和配置参数，提高系统的性能和稳定性，定期进行性能测试和分析，找到瓶颈并进行优化
- **故障排除**：当系统出现故障或异常情况时，能够快速发现和解决问题，通过建立故障排除机制和团队，使问题能够快速定位和解决
- **升级和维护**：及时更新系统的各个组件和软件版本，以保证系统的功能和性能不断提升，定期对系统进行维护和修复

## 与相关概念的关系

质量属性是[[concepts/software-architecture|软件架构]]设计的核心关注点之一，与以下概念紧密相关：

- [[concepts/quality-requirements|质量需求]]：质量属性是质量需求的具体化表达

- [[concepts/non-functional-requirements|非功能性需求]]：质量属性是NFR的重要组成部分

## 实际应用

在[[concepts/software-architecture|软件架构设计]]过程中，架构师需要：

1. 识别利益相关者关心的质量属性
2. 为每种关键属性定义具体的场景
3. 选择适当的[[concepts/architectural-tactics|架构策略]]来满足场景需求
4. 在[[concepts/architecture-evaluation|架构评估]]中验证设计是否满足质量目标

质量属性场景是连接业务需求与架构设计的重要桥梁，确保架构决策有明确的质量目标导向。不同的系统类型（如[[summaries/16.2.2 Web应用架构分类|Web应用]]、大数据处理系统等）对质量属性的侧重有所不同，需要根据具体业务场景进行权衡和取舍。
