# 用户故事：敏捷开发中的需求描述方法

## 概述

用户故事（User Story）是[[敏捷开发]]方法论中用于描述用户需求的核心技术。它以简洁的叙事形式，表达系统应当为用户提供的价值。不同于传统冗长的需求文档，用户故事强调与用户的对话交流，而非书面合同的束缚。

## 用户故事的三个方面

完整的用户故事应包含三个层面的内容：

1. **书面描述**：用于项目计划和备忘的简短说明，通常遵循"作为...我想要...以便..."的格式
2. **交谈**：与用户面对面或在线讨论，以细化故事的具体细节
3. **测试用例**：用于验证故事是否正确实现的验收标准

## 用户故事的六个基本属性

根据[[summaries/11.2.6需求记录技术]]，用户故事具有以下核心属性：

| 属性 | 说明 |
|------|------|
| **独立性** | 尽可能避免故事之间存在依赖关系，因为依赖会产生优先级和规划问题 |
| **可协商性** | 用户故事是可协商的，不是必须实现的书面合同或固定需求 |
| **对用户有价值** | 确保每个故事对用户有价值的最好方式是让用户亲自编写故事 |
| **可预测性** | 系统分析师应能预测故事的规模以及实现所需的工作量 |
| **短小精悍** | 故事规模取决于开发团队的能力和技术实现等方面 |
| **可测试性** | 所编写的故事必须是可测试的，能够明确验证是否完成 |

## 用户故事与传统需求文档的区别

用户故事描述的传统形式是手工书写的用户故事卡。系统分析师的职责是辅助用户编写故事，而非替用户编写。关键认知是：用户所编写的故事是进一步讨论的引子，而不是详细的需求规范。

## 最佳实践

- 在编写故事之前应建立用户角色模型
- 必须包含对项目成功至关重要的角色
- 尽量保证所有用户对系统完全满意
- 由用户团队根据故事的重要性安排开发工作
- 用户团队负责回答所有开发问题
