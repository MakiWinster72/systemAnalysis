# 多任务调度机制

## 定义

多任务调度机制是操作系统协调多个任务（或进程）共享处理器资源的核心机制，通过特定算法决定在任意时刻由哪个任务占用CPU执行，是[[concepts/嵌入式实时系统]]能够满足时间约束的关键技术。在[[summaries/17.4.4系统分析与设计]]中，软件子系统设计强调合理的任务划分直接影响软件质量，需要根据应用的实时性要求、应用场合、可用资源情况等诸多约束进行综合考虑。

多任务调度机制涉及[[进程管理]]的各个环节，包括进程/任务的创建、状态转换、调度执行以及终止。当多个任务竞争CPU和共享资源时，调度机制必须处理[[优先级反转]]等同步问题，确保系统的时间可预测性和正确性。

## 进程与任务状态模型

### 三态模型

在多道程序系统中，进程在处理器上交替运行，状态不断发生变化。一般有三种基本状态：

| 状态 | 说明 |
|------|------|
| **运行态 (Running)** | 进程在处理机上运行，单处理机系统中只有一个运行态进程 |
| **就绪态 (Ready)** | 进程获得除处理机外的所有资源，一旦获得处理机即可运行 |
| **阻塞态 (Blocked)** | 进程等待某一事件发生（如I/O请求），即使分配处理机也无法运行 |

三态模型中，状态转换包括：运行→阻塞（等待事件）、运行→就绪（时间片到）、就绪→运行（被调度）、阻塞→就绪（等待事件发生）。

### 五态模型

实际系统更复杂，引入新建态和终止态构成五态模型：

- **新建态 (New)**：进程刚被创建，尚未提交到就绪队列。创建进程分两个阶段——创建管理信息和进入就绪状态。引入新建态可根据系统性能和主存容量限制推迟进程提交。
- **终止态 (Terminated)**：进程终止分两个阶段——等待操作系统善后处理和释放主存。

状态转换包括：新建→就绪、就绪→运行→终止、运行→阻塞→就绪。

## 核心要素

### 1. 时间参数

[[summaries/17.3.2多任务调度算法]] 中定义的时间指标：

| 时间指标 | 含义 |
|---------|------|
| 中断延迟时间 | 中断发生到系统获知的时间 |
| 中断响应时间 | 中断发生到执行中断服务例程的时间 |
| 中断恢复时间 | 中断结束到恢复被中断代码的时间 |
| 任务响应时间 | 中断产生到任务真正开始运行的时间 |
| 系统响应时间 | 发出请求到系统应答的时间（调度延迟） |

### 2. [[concepts/任务优先级]]

任务优先级决定了调度顺序：
- **静态优先级**：设计时确定，运行期间不变
- **动态优先级**：运行时可动态调整

在可抢占式系统中，高优先级任务可中断低优先级任务的执行。然而，这种机制在面对[[优先级反转]]问题时可能导致高优先级任务被意外阻塞。

### 3. [[进程控制块]]

进程是程序的一次执行，由进程控制块（PCB）、程序和数据组成。PCB是进程存在的唯一标志，系统通过PCB管理进程。程序部分描述进程需要完成的功能；数据部分包括程序执行时所需的变量和工作区。

## 软件子系统设计中的任务划分

根据[[summaries/17.4.4系统分析与设计]]，嵌入式系统的软件设计需要根据应用的实时性要求进行合理的任务划分，这是多任务调度的基础。任务划分的力度和数目的合理性直接决定着调度开销和任务之间的通信开销，以及系统响应时间。

### 任务划分步骤

#### 第一步：明确实时性指标

确定系统是软实时还是硬实时，以及最坏情况下的实时时限。同时确定任务大体的数目，这需要充分考虑极端情况下的各种因素。**实时系统的软件应该尽可能简化**，过于复杂的软件设计会增加系统的复杂性，从而降低可靠性。

#### 第二步：可调度性分析

对已划分任务进行功能特点分类，识别具有硬实时性要求的关键任务，赋予适当的优先级。根据每个任务执行的时间估计值，在考虑调度开销余量的条件下进行粗略的可调度性分析，确保所有关键任务都满足调度时限。

**任务合并与分裂原则：**

| 策略 | 说明 |
|------|------|
| 周期相同合并 | 对于周期相同的所有任务功能组合成一个单独任务，降低事件分发机制开销 |
| 顺序执行合并 | 对于固定顺序执行的任务合成单一任务，避免同步开销 |
| 事件源合并 | 将有相同事件源触发的任务合并，减小事件分发机制开销 |
| 计算密集分离 | 将计算密集型或以数据处理为主的功能独立出来，由一个优先级的任务实现 |
| 同步互斥优化 | 对任务之间的同步与互斥机制进行分析，尽量避免大粒度的互斥锁 |

#### 第三步：优先级分配

根据[[summaries/17.4.4系统分析与设计]]，任务优先级分配的一般原则如下：

- **与中断的关联性**：凡是与中断服务程序相关联的任务应安排尽量高的优先级，以保证及时处理异步事件，提高系统的实时响应能力。
- **紧迫性**：越是紧迫的任务对响应时间的要求越严格，对于所有紧迫任务，根据响应时间的先后顺序安排优先级。
- **任务的频繁性**：对于周期性任务，执行越频繁则周期越短，允许耽搁的时间也越短，故相应优先级也应越高。
- **传递性**：信息处理流程的前驱任务优先级应高于后继任务。

## 调度算法分类体系

根据[[summaries/17.3.2多任务调度算法]]，调度算法可按多个维度分类：

```
调度算法分类
├── 按时限性质：软时限 / 硬时限
├── 按周期性：周期性 / 非周期性
├── 按可抢占性：可抢占 / 非抢占
├── 按优先级确定：静态 / 动态
└── 按调度时机：在线 / 离线
```

### 静态调度算法

| 算法 | 特点 |
|------|------|
| [[concepts/RMS调度算法]] | 周期越短，优先级越高；CPU利用率上限约70% |
| 分区APPS调度 | 面向航空电子IMA系统的时间片分配 |
| 时间轮转调度 | 同优先级任务均分CPU时间 |

### 动态调度算法

| 算法 | 特点 |
|------|------|
| [[concepts/EDF调度算法]] | 截止时间越近，优先级越高；CPU利用率可达100% |

## [[优先级反转]]

优先级反转是指由于资源竞争，低优先级任务在执行而高优先级任务等待的现象。当具有不同优先级的任务存在相互依赖关系时，就可能发生优先级反转。

### 问题场景

以任务A（高优先级）、任务B（中优先级）、任务C（低优先级）为例：
1. 任务C首先获得共享资源S
2. 任务A请求资源S，被迫等待任务C
3. 任务B进入就绪，抢占任务C的CPU
4. 任务A必须等待任务B和任务C都执行完毕

此时，任务A的优先级实际降到了任务C的水平，发生优先级反转。

### 类型划分

| 类型 | 特征 |
|------|------|
| **无界优先级反转** | 中优先级任务抢占低优先级任务的时间不确定，可能造成高优先级任务无限期阻塞 |
| **有界优先级反转** | 低优先级任务占用资源的时间已知，阻塞时间有上界 |

## 资源同步与通信

### 资源同步协议

为解决[[优先级反转]]问题，需要采用资源控制协议来管理共享资源的访问：

#### 优先级继承协议

当低优先级任务占有高优先级任务请求的资源时，T的优先级临时提升到被阻塞任务中最高优先级的等级。退出临界区后恢复原优先级。

**特点：**
- 阻塞时间有界
- 可能出现阻塞链
- 可能导致死锁

#### 优先级天花板协议

优先级天花板是指控制访问临界资源的信号量的优先级，定义为所有使用该信号量的任务中最高优先级的优先级。

**优势：**
- 不会产生阻塞链
- 不会发生死锁
- 每个请求任务最多被阻塞一次

#### 协议对比

| 特性 | 优先级继承协议 | 优先级天花板协议 |
|------|--------------|----------------|
| 阻塞链 | 可能出现 | 不会出现 |
| 死锁 | 可能 | 不会 |
| 阻塞次数 | 可能多次 | 最多一次 |

### 进程间通信

多任务系统中的进程间通信方式分为低级和高级两种：

**低级通信**以[[PV操作]]为代表，存在编程难度大和效率低的问题，可能引起死锁。

**高级通信方式**包括：

| 方式 | 说明 |
|------|------|
| **共享存储模式** | 相互通信的进程共享某些数据结构或存储区 |
| **消息传递模式** | 进程间数据交换以消息为单位（如Send/Receive原语） |
| **管道通信** | 通过共享文件（pipe）实现进程间字符流通信 |

## [[concepts/上下文切换]]

任务切换涉及[[concepts/上下文切换]]机制：
- 保存当前任务的寄存器、堆栈等上下文
- 恢复即将运行任务的上下文
- 在可抢占式调度中，中断恢复时间需包含任务切换开销

## 死锁处理

死锁是两个以上进程互相等待对方资源而无法继续运行的现象。产生死锁的四个必要条件：

1. **互斥条件**：资源每次只允许一个进程使用
2. **不剥夺条件**：进程已占用资源不会被强制剥夺
3. **请求与保持条件**：进程请求新资源时不主动释放已占用资源
4. **环路条件**：环路中每个进程在请求另一个进程已占有的资源

### 处理策略

| 策略 | 方法 |
|------|------|
| **死锁预防** | 破坏四个必要条件之一（如预先静态分配法、资源有序分配法） |
| **死锁避免** | 使用[[银行家算法]]检测资源分配后系统是否进入安全状态 |
| **检测与解除** | 允许死锁发生但定时检测，采用资源剥夺法或撤销进程法解除 |

## [[线程]]

引入线程是为了减少进程创建、撤销和切换的开销。线程作为调度和分配的基本单位，进程作为独立分配资源的单位。线程基本不拥有资源，只拥有程序计数器、寄存器和栈等必要资源，可与同属进程的其他线程共享全部资源。

线程分为用户级线程（不依赖内核）和内核支持线程（依赖内核）两类。由于线程具有轻量级特性，故又称"轻型进程（Light-Weight Process）"。

## 可调度性分析

[[concepts/实时系统可调度性]]是验证系统能否满足时限要求的关键：

1. **利用率分析法**：计算任务CPU利用率，与理论上限比较
2. **RMS定理**：Σ(Ei/Ti) < n(2^(1/n) - 1)
3. **EDF充分必要条件**：基于动态优先级的可调度性判断

使用资源同步协议时，可调度性分析还需考虑协议引入的额外阻塞时间。

## 设计考量

设计多任务调度系统时需平衡：

- **确定性**：任务调度的可预测性，防止无界优先级反转
- **正确性**：正确处理资源同步，避免死锁和时序反常
- **效率**：减少调度开销，提升CPU利用率
- **灵活性**：适应变化的系统情况
- **公平性**：同等优先级任务获得平等执行机会

在进行[[summaries/17.4.4系统分析与设计]]时，还需要配合[[summaries/17.4.3软硬件协同设计]]，确保软件子系统设计符合整体系统架构的要求。
