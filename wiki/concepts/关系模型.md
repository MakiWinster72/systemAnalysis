# 关系模型

## 定义

关系模型（Relational Model）是[[summaries/5.2.1关系的基本概念|关系数据库]]的理论基础，是一种基于数学集合论的数据模型。系统而严格地提出关系模型的是美国IBM公司的**E.F.Codd**，他于1970年发表了划时代的论文《A Relational Model of Data for Large Shared Data Banks》。

在关系模型中，实体以及实体间的联系都是用关系来表示的。关系的描述称为**关系模式**，通常简记为 R(A₁, A₂, ..., Aₙ)，其中R为关系名，Aᵢ为属性名。关系是关系模式在某一时刻的状态或内容，即关系模式是型，关系是它的值。关系模式是静态的、稳定的，而关系是动态的、随时间不断变化的，因为关系操作在不断地更新着数据库中的数据。

> 在实际应用中，通常将关系模式和关系统称为关系，需从上下文加以区别。

一个领域内所有实体及其联系的关系集合构成[[concepts/关系数据库]]。

## 组成部分

关系模型由以下三部分组成：

1. **关系数据结构**：即二维表结构，用表格来描述实体及其联系
2. **关系操作集合**：包括[[concepts/关系代数]]和[[concepts/关系演算]]等查询操作
3. **关系完整性规则**：保证数据的正确性和一致性

## 概念设计与E-R模型

关系模型的理论基础是[[concepts/ER模型]]（Entity-Relationship Model），也称为E-R图，是描述概念世界、建立概念模型的实用工具。E-R图通过图形化的方式描述实体及其之间的联系，是数据库概念设计阶段的核心技术。

### E-R图三要素

| 要素 | 表示方法 | 说明 |
|------|---------|------|
| **实体（型）** | 矩形框 | 框内标注实体名称 |
| **属性** | 椭圆形 | 单值属性用实线椭圆；多值属性在虚线椭圆外套实线椭圆；派生属性用虚线椭圆表示 |
| **联系** | 菱形框 | 框内标注联系名称，连线标注联系类型 |

### 联系的类型

E-R图中的联系分为三种类型：

| 联系类型 | 说明 | 示例 |
|---------|------|------|
| **一对一（1:1）** | A中每个实体至多与B中一个实体有联系，反之亦然 | 班级与班主任 |
| **一对多（1:n）** | A中每个实体可与B中多个实体联系，B中每个实体至少与A中一个实体联系 | 班级与学员 |
| **多对多（m:n）** | A和B中每个实体都可与对方多个实体联系 | 学员与课程 |

### E-R图的集成

在数据库概念设计过程中，首先设计各子系统的局部E-R图，然后综合成系统的总体E-R图（视图集成）。集成方式包括：

- **一次集成**：将多个局部E-R图一次合并，复杂度高
- **逐步集成**：每次集成两个局部E-R图，降低复杂度

各局部E-R图之间可能存在冲突，主要有三类：

| 冲突类型 | 具体表现 | 解决方法 |
|---------|---------|---------|
| **属性冲突** | 属性域冲突、属性取值冲突 | 各部门协商统一 |
| **命名冲突** | 同名异义、异名同义 | 通过行政手段协商 |
| **结构冲突** | 同一对象不同抽象、属性个数或次序不同 | 将属性与实体互相转换；取各局部E-R图属性的并集 |

> 注意：冗余数据和冗余联系会破坏数据库完整性，应当予以消除。

## E-R图向关系模式的转换

E-R图向关系模式的转换属于数据库逻辑设计阶段的工作，需要将[[concepts/ER模型]]转换为[[summaries/5.2.2关系模型]]能处理的关系模式。

### 基本转换规则

| 联系类型 | 转换为独立关系模式 | 与某端合并 |
|---------|-------------------|-----------|
| **实体** | 实体的属性即为关系属性，主键即为关系主键 | — |
| **1:1联系** | 各实体主键和联系属性均为键属性 | 在某端关系模式中加入另一端主键和联系属性 |
| **1:n联系** | 主键为n端实体的主键 | 在n端关系模式中加入1端主键和联系属性 |
| **m:n联系** | 主键为各实体主键的组合 | — |
| **多元联系（3个以上实体）** | 主键为各实体主键的组合 | — |

### 特殊情况处理

| 情况 | 处理方法 |
|------|---------|
| **多值属性** | 将多值属性提升为弱实体，或将实体主键与多值属性单独构成一个关系模式 |
| **BLOB型属性** | 将BLOB属性与关系的主键独立为一个关系模式（优化考虑） |
| **派生属性** | 通常不转换派生属性，因可由其他属性计算得出 |
| **面向对象模型** | 关系模式对应类，关系模式的属性对应类的属性 |

## 基本术语

关系模型中涉及的基本概念包括：

| 术语 | 说明 |
|------|------|
| **属性** | 描述实体特征的概念，如学号、姓名等 |
| **域** | 属性的取值范围，必须是原子数据 |
| **目/度** | 二维表中属性的个数 |
| **候选码** | 能唯一标识元组的属性或属性组 |
| **主码** | 从候选码中选定的一个 |
| **主属性** | 包含在候选码中的属性 |
| **外码** | 引用其他关系码的属性 |
| **全码(All-key)** | 所有属性组构成候选码，用于无法仅用部分属性唯一标识元组的场景 |

## 关系代数运算

[[concepts/关系代数]]是关系模型的操作部分，提供8种基本运算：

### 集合运算

| 运算 | 符号 | 说明 |
|------|------|------|
| [[concepts/并运算|并]] | ∪ | R∪S的元组包括R和S所有元组的集合（要求两者有相同元/列数） |
| [[concepts/差运算|差]] | − | R−S的元组包括R中有而S中没有的元组 |
| [[concepts/交运算|交]] | ∩ | R∩S的元组包括R和S相同的元组 |

### 构造运算

| 运算 | 符号 | 说明 |
|------|------|------|
| [[concepts/笛卡儿积|笛卡儿积]] | × | R( m元)×S( n元) = (m+n)元元组集合，若R有u个元组，S有v个元组，结果有u×v个元组 |
| [[concepts/投影运算|投影]] | π | 从关系中抽取指定属性(列)，从列的角度进行运算 |
| [[concepts/选择运算|选择]] | σ | 从元组(行)角度筛选满足条件的记录，条件是逻辑表达式 |

### 连接运算

| 运算 | 说明 |
|------|------|
| **θ连接** | 从两个关系的笛卡儿积中选取属性间满足条件θ的元组 |
| **等值连接** | θ为"="时的特殊情况，选取属性值相等的元组 |
| **自然连接** | 特殊的等值连接，要求比较的分量必须是相同的属性组，并在结果中去除重复属性列 |

### 除运算

设有关系 R(X,Y) 与关系 S(Z)，Y和Z具有相同的属性个数且对应属性出自相同域。R÷S所得的商关系是R在属性X上投影的一个子集，该子集与S(Z)的笛卡儿积必包含在R(X,Y)中。

## 事务与并发控制

关系模型在理论上定义了数据的组织方式和操作方法，而具体实现时需要支持事务机制来保证数据一致性和完整性。

### 事务概念

事务是[[concepts/事务控制]]运行的基本工作单位，是用户定义的数据库操作序列，这些操作序列要么全做，要么全不做，是一个不可分割的工作单位。事务具有以下[[ACID特性]]：

- **原子性(Atomicity)**：事务的更新操作是不可分割的整体，不能部分完成
- **一致性(Consistency)**：事务执行使数据库从一个一致性状态转到另一个一致性状态
- **隔离性(Isolation)**：并发事务互不干扰，执行结果等价于串行调度，具有[[可串行性]]
- **持久性(Durability)**：事务一旦提交，改变永久保存

### 并发问题

多个事务并发执行时会产生以下数据不一致问题：

| 问题 | 说明 |
|------|------|
| **丢失修改** | 多个事务同时读取和修改同一数据，后提交的事务覆盖先提交事务的修改 |
| **读"脏数据"** | 事务A修改数据后被撤销，但事务B已读取了该未最终提交的数据 |
| **不可重复读** | 事务A两次读取数据之间，事务B修改了该数据，导致两次结果不同 |

### 封锁技术

处理并发控制的主要方法是封锁技术，包括：

- **X封锁（排他型封锁）**：允许事务读写数据，阻止其他事务任何类型的封锁
- **S封锁（共享型封锁）**：允许并发读取，但阻止修改

常见的[[concepts/封锁协议]]包括：

| 协议 | 能防止的问题 |
|------|-------------|
| 一级封锁协议 | 丢失修改 |
| 二级封锁协议 | 丢失修改、读"脏数据" |
| 三级封锁协议 | 丢失修改、读"脏数据"、不可重复读 |
| 两段锁协议 | 保证可串行化调度 |

## 特点

- **数学基础**：应用数学方法来处理数据库中的数据，最早可追溯到1962年CODASYL发表的"信息代数"
- **概念清晰**：关系模式与关系严格区分，静态与动态分明
- **操作完备**：关系代数提供8种基本运算，足以表达任何查询
- **设计规范**：通过[[concepts/ER模型]]进行概念设计，通过规范化理论减少数据冗余
- **事务支持**：关系数据库系统通过封锁协议支持事务的ACID特性，保证并发操作的数据一致性
- **应用广泛**：目前应用最广泛的数据模型
- **产品众多**：Oracle、DB2、SQL Server、MySQL等都是关系数据库系统

## 与其他数据模型的比较

关系模型相比层次模型和网状模型，具有概念简单、数据独立性高的优点。相比[[concepts/面向对象模型]]，关系模型更成熟、理论基础更完善，目前仍是主流。E-R模型提供了从概念设计到逻辑设计的完整方法论，通过E-R图进行概念建模，再转换为关系模式，是数据库设计的主流方法。但在处理复杂对象方面，面向对象模型有独特优势，许多关系数据库（如Oracle）正在增加对对象模型的支持。
