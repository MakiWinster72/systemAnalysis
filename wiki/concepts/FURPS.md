# FURPS+需求分类模型与架构评估维度

FURPS+ 是一种在[[concepts/统一过程]]（UP）中使用的软件需求分类模型，通过多维度对系统需求进行系统化组织和划分。同时，作为[[软件架构评估]]的重要理论依据，FURPS+与面向架构评估的质量属性维度相互补充，共同构成软件架构质量属性的理论基础。

## 模型组成

FURPS+ 由两大部分组成：FURPS核心五类需求加上"+"扩展因素。

### FURPS核心类别

| 类别 | 英文 | 含义 | 包含要素 |
|------|------|------|----------|
| **功能性** | Functional | 系统提供的核心功能 | 特性、功能、安全性 |
| **可用性** | Usability | 用户使用系统的便捷程度 | 人性化因素、帮助、文档 |
| **可靠性** | Reliability | 系统稳定运行的能力 | 故障频率、可恢复性、可预测性 |
| **性能** | Performance | 系统的响应表现 | 响应时间、吞吐量、准确性、资源利用率 |
| **可支持性** | Supportability | 系统维护和扩展能力 | 适应性、可维护性、国际化、可配置性 |

## 面向架构评估的质量属性维度

根据[[summaries/12.6.1质量属性概念]]和架构评估实践，评估方法普遍关注以下8种质量属性：

### 1. 性能（Performance）

系统的响应能力，即要经过多长时间才能对某个事件做出响应，或者在某段时间内系统所能处理的事件的个数。常用指标：
- **单位时间事务处理量**：系统吞吐量
- **事务处理时间**：响应速度

性能测试经常要使用基准测试程序进行定量评估。

### 2. 可靠性（Reliability）

软件系统在应用或系统错误面前，在意外或错误使用的情况下维持软件系统的功能特性的基本能力。可靠性是最重要的软件特性，通常用以下指标衡量：

- **MTTF**（Mean Time To Failure）：平均无故障时间
- **MTBF**（Mean Time Between Failures）：平均故障间隔时间

> 在失效率为常数和修复时间很短的情况下，MTTF和MTBF几乎相等。

可靠性包含两个维度：

| 维度 | 目的 | 说明 |
|------|------|------|
| **容错** | 错误发生时确保系统正确行为 | 进行内部"修复"，如分布式系统失去连接后恢复连接并重新执行操作 |
| **健壮性** | 保护系统不受错误使用和错误输入影响 | 确保系统处于预先定义好的状态，按已定义方式终止执行 |

**架构影响**：软件架构对可靠性有巨大影响，可通过在应用程序内部采用[[冗余机制]]，或集成监控构件和[[异常处理]]，以提升系统可靠性。

### 3. 可用性（Availability）

系统能够正常运行的时间比例，经常用以下方式表示：
- 两次故障之间的时间长度
- 系统出现故障时能够恢复正常的速度

可用性会受到系统错误、恶意攻击和高负载等问题的影响。

### 4. 安全性（Security）

系统在向合法用户提供服务的同时能够阻止非授权用户使用的企图或拒绝服务的能力。安全性根据系统可能受到的安全威胁类型来分类，可划分为：

| 特性 | 说明 |
|------|------|
| **机密性** | 保证信息不泄露给未授权的用户、实体或过程 |
| **完整性** | 保证信息的完整和准确，防止信息被非法修改 |
| **不可否认性** | 信息交换双方不能否认其在交换过程中发送或接收信息的行为 |
| **可控性** | 保证对信息的传播及内容具有控制的能力，防止为非法者所用 |

### 5. 可修改性（Modifiability）

能够快速地以较高的性价比对系统进行变更的能力，通常以某些具体的变更为基准，通过考察变更的代价来衡量。可修改性包含以下4个方面：

| 方面 | 英文 | 关注点 |
|------|------|--------|
| **可维护性** | Maintainability | 问题的修复：在错误发生后"修复"软件系统。支持局部性修改，使修改对其他构件的负面影响最小化 |
| **可扩展性** | Extendibility | 使用新特性扩展系统，替换构件并删除不需要的特性和构件。需要松散耦合的构件，使开发人员在不影响构件客户的情况下替换构件 |
| **结构重组** | Reassemble | 重新组织软件系统的构件及构件间的关系，如移动构件到不同子系统。需要精心设计构件之间的关系，允许灵活配置而不影响主体实现 |
| **可移植性** | Portability | 使软件系统适用于多种硬件平台、用户界面、操作系统、编程语言或编译器。需要按硬件、软件无关的方式组织软件系统 |

### 6. 功能性（Functionality）

系统完成所期望工作的能力。一项任务的完成需要系统中许多或大多数构件的相互协作。

### 7. 可变性（Changeability）

架构经扩充或变更而成为新架构的能力。这种新架构应该符合预先定义的规则，在某些具体方面不同于原有的架构。

当要将某个架构作为一系列相关产品（例如，[[软件产品线]]）的基础时，可变性是很重要的。

### 8. 互操作性（Interoperability）

作为系统组成部分的软件不是独立存在的，通常与其他系统或自身环境相互作用。为了支持互操作性，软件架构必须为外部可视的功能特性和数据结构提供精心设计的软件入口。

程序和用其他编程语言编写的软件系统的交互作用就是互操作性，这种互操作性也影响应用软件的架构。

## 质量属性场景：需求规格化的结构化方法

为了精确描述软件系统的质量属性，通常采用质量属性场景（Quality Attribute Scenario）作为描述质量属性的手段。质量属性场景是一个具体的质量属性需求，是利益相关者与系统的交互的简短陈述。

### 质量属性场景的六要素

质量属性场景由以下六部分组成：

| 要素 | 说明 | 典型取值 |
|------|------|----------|
| **刺激源** | 生成该刺激的实体 | 人、计算机系统、其他刺激器 |
| **刺激** | 刺激到达系统时需要考虑的条件 | 疏忽、错误、崩溃、时间 |
| **环境** | 刺激发生时的条件 | 正常操作、降级模式、超载 |
| **制品** | 被激励的对象 | 系统处理器、通信信道、持久存储器 |
| **响应** | 激励到达后采取的行动 | 检测事件、记录通知、禁止事件源 |
| **响应度量** | 对响应进行度量的方式 | 可用时间间隔、故障修复时间 |

质量属性场景将抽象的质量属性需求转化为具体、可度量、可测试的场景，是连接[[软件架构评估]]与质量需求的重要桥梁。

### 六类质量属性场景的详细描述

#### 可用性质量属性场景

| 要素 | 可能的取值 |
|------|-----------|
| 刺激源 | 系统内部、系统外部 |
| 刺激 | 疏忽、错误、崩溃、时间 |
| 环境 | 正常操作、降级模式 |
| 制品 | 系统处理器、通信信道、持久存储器、进程 |
| 响应 | 检测事件并记录通知；禁止导致错误或故障的事件源；在一段预先指定的时间间隔内不可用 |
| 响应度量 | 系统必须可用的时间间隔、可用时间、降级模式运行时间、故障修复时间 |

#### 可修改性质量属性场景

| 要素 | 可能的取值 |
|------|-----------|
| 刺激源 | 最终用户、开发人员、系统管理员 |
| 刺激 | 增加、删除、修改、改变功能、质量属性、容量 |
| 环境 | 系统设计时、编译时、构建时、运行时 |
| 制品 | 系统用户界面、平台、环境或与目标系统交互的系统 |
| 响应 | 查找架构中需要修改的位置；进行修改且不影响其他功能；对修改进行测试和部署 |
| 响应度量 | 人力成本、修改所需时间、资金成本 |

#### 性能质量属性场景

| 要素 | 可能的取值 |
|------|-----------|
| 刺激源 | 用户请求、其他系统触发 |
| 刺激 | 定期事件到达、随机事件到达、偶然事件到达 |
| 环境 | 正常模式、超载模式 |
| 制品 | 系统 |
| 响应 | 处理刺激、改变服务级别 |
| 响应度量 | 等待时间、期限、吞吐量、抖动、缺失率、数据丢失率 |

#### 可测试性质量属性场景

| 要素 | 可能的取值 |
|------|-----------|
| 刺激源 | 开发人员、系统验证人员、客户验收测试人员 |
| 刺激 | 已完成的分析、架构、设计、类和子系统集成；所交付的系统 |
| 环境 | 设计时、开发时、编译时、部署时 |
| 制品 | 设计、代码段、完整的应用 |
| 响应 | 提供对状态值的访问、提供所计算的值、准备测试环境 |
| 响应度量 | 已执行语句的百分比、缺陷出现故障的概率、执行测试的时间、准备测试环境的时间 |

#### 易用性质量属性场景

| 要素 | 可能的取值 |
|------|-----------|
| 刺激源 | 最终用户 |
| 刺激 | 学习系统特性、有效使用系统、使错误的影响最低、适配系统、对系统满意 |
| 环境 | 系统运行时或配置时 |
| 制品 | 系统 |
| 响应 | 帮助系统与环境联系紧密；数据和命令的聚合；撤销、取消、从故障中恢复；定制能力；显示系统状态 |
| 响应度量 | 任务时间、错误数量、解决问题数量、用户满意度、用户知识获得 |

#### 安全性质量属性场景

| 要素 | 可能的取值 |
|------|-----------|
| 刺激源 | 正确识别/非正确识别/身份未知的个人或系统 |
| 刺激 | 试图显示数据、改变/删除数据、访问系统服务、降低系统服务可用性 |
| 环境 | 在线或离线、联网或断网、连接有防火墙或直接连到网络 |
| 制品 | 系统服务、系统中的数据 |
| 响应 | 对用户身份认证；隐藏用户身份；阻止/允许对数据或服务的访问；以不可读格式存储数据 |
| 响应度量 | 避开安全防范措施所需时间/努力/资源；检测到攻击的可能性；在拒绝服务攻击下仍获得服务的百分比 |

## FURPS+与架构评估属性的对应关系

| FURPS+类别 | 架构评估质量属性 | 细化维度 |
|-------------|-----------------|----------|
| 功能性 | 功能性 | 系统完成所期望工作的能力 |
| 可用性 | 可用性 | 系统正常运行时间比例、故障恢复速度 |
| 可靠性 | 可靠性 | MTTF/MTBF、容错性、健壮性 |
| 性能 | 性能 | 响应时间、吞吐量、资源利用率 |
| 可支持性 | 可修改性+互操作性 | 可维护性、可扩展性、结构重组、可移植性、互操作性 |
| — | 可变性 | 架构扩充或变更能力 |
| — | 安全性 | 机密性、完整性、不可否认性、可控性 |

## 质量属性的生命周期视角

基于软件系统生命周期，[[summaries/12.6.1质量属性概念]]将质量属性分为两个维度：

### 开发期质量属性

主要指软件开发阶段所关注的质量属性：

- **易理解性**：设计被开发人员理解的难易程度
- **可扩展性**：适应新需求或需求变化而增加新功能的能力
- **可重用性**：重用软件系统或某一部分的难易程度
- **可测试性**：对软件测试以证明其满足需求规范的难易程度
- **可维护性**：识别修改点并实施修改的难易程度
- **可移植性**：将软件系统从一个运行环境转移到另一个不同运行环境的难易程度

### 运行期质量属性

主要指软件运行阶段所关注的质量属性：

- **性能**：及时提供相应服务的能力（速度、吞吐量、容量）
- **安全性**：兼顾向合法用户提供服务与阻止非授权使用的能力
- **可用性**：系统正常运行时间比例
- **可靠性**：系统在错误面前的维持能力

## 应用价值

FURPS+模型结合架构评估质量属性维度和质量属性场景方法的应用价值在于：

1. **全面覆盖**：确保需求分析和架构设计时不会遗漏重要的质量维度
2. **结构化组织**：将分散的质量需求按类别归类，便于管理和追踪
3. **精确描述**：质量属性场景提供六要素结构化方法，将抽象质量属性转化为具体场景
4. **度量指导**：为各质量属性提供具体的度量指标（如MTTF、MTBF、响应时间）
5. **架构衔接**：为[[软件架构评估]]提供从需求到验证的完整链条
6. **架构影响分析**：明确哪些架构设计能够提升特定质量属性（如冗余机制提升可靠性）

## 实践要点

在实际应用中，使用FURPS+模型、架构评估质量属性和质量属性场景方法时应当注意：

- 功能性需求和非功能需求往往相互影响，需要综合考虑
- 质量指标应当具体可度量，如响应时间"不超过3秒"、MTTF"大于1000小时"
- 可靠性指标（MTTF、MTBF）需要在失效率常数和修复时间短的条件下才几乎相等
- 容错与健壮性有区别：容错确保错误发生时继续运行，健壮性只保证按预定方式终止
- 可支持性需要考虑系统的长期维护和演化需求
- 在编写SRS时，应结合FURPS+分类和质量属性场景进行标准化表达
- 质量属性场景的六要素（刺激源、刺激、环境、制品、响应、响应度量）为质量需求提供了结构化描述模板
- 架构设计时可通过[[冗余机制]]和[[异常处理]]主动提升系统可靠性
