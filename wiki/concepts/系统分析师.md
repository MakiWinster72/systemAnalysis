# 系统分析师

## 定义

系统分析师是软件工程和信息系统开发中的关键角色，负责理解用户需求、分析现有系统、设计新系统解决方案。他们是连接业务需求与技术实现的桥梁，在系统开发生命周期中发挥核心作用。

## 核心职责

- **理解用户需求**：协助用户明确原始需求，帮助用户想象未来软件应提供的功能
- **分析现有系统**：厘清信息流程，识别制约现有系统的瓶颈问题
- **抽象逻辑模型**：通过调查分析，抽象出新系统的逻辑模型，锁定系统边界、功能、处理过程和信息结构
- **沟通协调**：促进系统所有者、用户与技术团队之间的有效交流
- **推动因果分析**：作为推动者，引导系统所有者和用户深入分析问题的原因与结果，而非直接陈述解决方案
- **制定系统改进目标**：与用户共同定义精确、可度量的系统改进目标，确定可能限制目标实现的约束条件
- **汇报调查结果**：在问题分析阶段末期，向业务团队汇报调查结果和建议，主持书面报告的编写

## 案例分析考试中的职责

系统分析师在实际工作中需要综合运用多种能力，案例分析考试正是对这些能力的全面考察：

### 问题分析能力

从复杂业务场景中提取关键需求是系统分析师的核心技能。在案例分析中，需要：
- 识别业务背景和问题本质
- 厘清信息流程和系统边界
- 分析制约系统性能的关键因素

### 方案设计能力

提出可行的系统解决方案需要系统分析师具备：
- [[系统架构设计]] 能力，选择合适的架构模式
- [[数据库设计]] 与 [[数据建模]] 能力
- 权衡技术选型与业务需求

### 技术选型能力

根据约束条件选择合适的技术栈是系统分析师的重要职责，需要考虑：
- [[分布式系统设计]] 需求
- [[微服务架构]] 模式的适用性
- [[API设计]] 与集成方案
- [[安全设计原则]] 的落实
- [[性能优化]] 方案的制定

### 文档撰写能力

规范表达设计决策和理由是系统分析师的基本功，需要掌握：
- 可行性研究报告编写
- 需求规格说明撰写
- 技术方案文档编制

## 沟通管理职责

项目沟通管理是系统分析师工作的重要组成部分，其目标是及时而适当地创建、收集、发送、储存和处理项目的信息。系统分析师在沟通过程中需要同时扮演[[内部沟通]]和[[外部沟通]]的双重角色。

### 对内沟通

系统分析师需要与项目团队和睦相处，协助项目经理做好技术管理工作。具体包括：

- 协调团队内部的技术问题
- 参与项目进度管理
- 确保技术方案与业务需求一致
- 维护团队协作氛围

### 对外沟通

系统分析师需要与用户进行良好沟通，以便正确而快捷地获取用户需求，做好系统分析与设计工作。具体包括：

- 与用户建立信任关系
- 深入理解业务背景
- 收集和验证需求信息
- 反馈系统设计进展

### 沟通类型选择

| 类型 | 特点 | 适用场景 |
|------|------|----------|
| [[正式沟通]] | 通过项目组织明文规定的渠道进行，沟通效果好，有较强约束力 | 重要决策、正式报告、项目周报 |
| [[非正式沟通]] | 在正式渠道之外进行，沟通方便，速度快 | 日常协调、快速讨论、关系维护 |

系统分析师应根据沟通目的和情境选择合适的沟通方式，平衡沟通效率与约束力要求。

## 参与边界

系统分析师应明确自身的参与范围：

| 活动 | 系统分析师角色 | 说明 |
|------|----------------|------|
| 研究问题领域 | 主持者 | 主持工作，进行面谈，协调各方 |
| 因果分析 | 推动者 | 推动过程，不直接参与分析本身 |
| 制定系统改进目标 | 推动者 | 推动目标定义，协助识别约束条件 |
| 汇报调查结果和建议 | 推动者 | 与项目经理共同推动，编写书面报告 |
| 上下文图绘制 | 参与（部分） | 除非涉及技术限制分析，否则系统设计人员参与度更高 |
| 技术问题分析 | 视情况参与 | 仅在被要求分析当前系统技术限制时参与 |

**重要提醒**：系统分析师应避免在未真正分析问题之前就陈述解决方案（如"我们需要"或"我们想"），这实际上是以方案的形式陈述问题，而非真正的问题分析。

## 主要挑战

系统分析师面临三大核心挑战：

1. **知识鸿沟**：作为IT专家，缺乏足够的用户业务领域知识，容易被各种信息流程淹没，难以厘清头绪
2. **沟通障碍**：与用户所处行业不同，知识结构和经历差异导致交流困难，系统调查易出现遗漏和误解
3. **需求不确定性**：用户往往难以给出完整、正确的原始需求，前期分析不透彻会给系统带来极大损害

## 在研究问题领域中的作用

在[[summaries/10.4.1研究问题的领域]]中，系统分析师扮演核心角色：

- 主持研究问题的领域工作
- 进行面谈、记录调查结果
- 深入理解各方对系统的不同理解（详细程度、表述方式、感知、观点）
- 协调来自支持该系统和受其影响的所有业务部门的系统所有者和用户代表

## 因果分析中的角色

在[[summaries/10.4.2分析问题和机会]]中，系统分析师负责推动因果分析过程：

- 引导团队分析每个问题的**原因**和**结果**
- 结果可能是更深层问题的症状，需继续追溯
- 直到原因和结果不再引发其他问题
- 目标：得出对问题的真正理解，发现更有创造性和价值的方案

真正的[[因果分析]]需要系统所有者和用户主动参与，因为他们是问题领域专家。

## 制定系统改进目标

在问题分析过程中，系统分析师还需推动[[系统改进目标]]的制定：

- 目的：建立成功的准则，对系统的任何改进都将按照该准则进行度量
- 目标应精确、可度量地定义新系统预期的业务性能陈述
- 需同时确定已知的[[系统约束条件]]，包括以下四类：
  - **进度约束**：最终期限
  - **成本约束**：预算限制
  - **技术约束**：所需技术或技术兼容性要求
  - **政策约束**：组织政策或标准要求
- 系统设计人员和构造人员不参与此任务（此时仍不关心技术问题）

## 汇报调查结果和建议

问题分析阶段需要以[[沟通任务]]作为总结，系统分析师在其中的职责包括：

- **推动汇报会议**：与项目经理共同主持，向业务团队汇报调查结果和建议
- **确定与会人员**：包括整个项目团队（系统所有者、用户、分析员、设计人员、构造人员）
- **确保开放性**：会议应对所有感兴趣的业务人员开放
- **维护沟通渠道**：如果项目建立了内联网站，应在整个问题分析阶段不断维护，确保项目进展的持续沟通

### 书面报告标准结构

系统分析师通常需要编写或协助编写以下结构的书面报告：

| 章节 | 主要内容 | 篇幅 |
|------|----------|------|
| 总结 | 性能问题与因果分析、问题指示总结、系统改进目标简述 | 约2页 |
| 背景信息 | 面谈和会议人员清单、信息资源清单、分析技术说明 | 约2页 |
| 当前系统概述 | 战略意义、当前系统模型 | 约5页 |
| 当前系统分析 | 性能/信息/经济/控制/效率/服务等问题及因果分析 | 5~10页 |
| 详细建议 | 系统改进目标与优先级、约束条件、项目计划 | 5~10页 |
| 附录 | 接口模型、数据模型、地理模型、过程模型等 | 补充 |

## 与项目经理的关系

通常由项目经理领导、资深系统分析师主持研究工作。一个人同时扮演这两个角色十分常见。在汇报阶段，两者共同推动沟通任务。

## 需求获取能力

在需求获取过程中，系统分析师需要掌握多种技术手段：

### 用户访谈

用户访谈是最基本的需求获取手段，具有良好的灵活性，应用范围广泛。系统分析师需具备良好的沟通技巧，能够与关键人员有效交流，同时需要足够的领域知识。

### 问卷调查

当用户较多或关键人员时间有限时，系统分析师可借助问卷调查，通过精心设计调查表从大量干系人处收集信息。问卷调查的优势包括：
- 短时间内以低廉代价收集大量数据
- 允许匿名填写，获得更真实信息
- 结果便于整理和统计分析

设计高质量问卷需包含三个重要活动：确定问题及其类型、编写问题、设计问卷格式。最佳实践是将问卷调查与用户访谈结合使用，先通过问卷获得基础信息，再针对关键问题进行深入访谈。

### 其他方法

系统分析师还应掌握采样技术从现有系统文档中提取代表性信息，以及情节串联板技术帮助用户消除对信息系统的认知盲区。

## 项目管理能力

系统分析师需要掌握[[项目管理]]方法论，包括：

- 制定项目计划和时间表
- 识别和管理项目[[风险]]
- 协调资源分配
- 监控项目进度和质量

## 质量保证能力

系统分析师应关注[[质量保证]]策略：

- 制定质量标准和度量指标
- 确保系统设计满足非功能性需求
- 进行设计评审和验证

## 预测与决策支持

系统分析师利用预测技术为组织提供决策支持。通过对历史数据和当前现状进行分析，系统分析师可以预测未来的趋势和变化，支持战略决策。

### 科学预测的途径

系统分析师在进行预测分析时通常采用三种科学途径：

1. **因果分析**：通过研究事物的形成原因来预测事物未来发展变化的必然结果

2. **类比分析**：将单项技术的发展同生物的增长相类比，或将正在发展中的事物同历史上的"先导事件"相类比，预测事物未来发展

3. **统计分析**：运用数学方法对事物过去和现在的数据资料进行分析，去伪存真、由表及里，揭示历史数据背后的规律性，明确事物未来发展趋势

### 预测的应用领域

系统分析师运用预测能力服务于多个方面：
- 制订战略计划
- 优化业务流程
- 改进营销策略
- 提高生产效率
- 进行风险评估，确定企业或组织可能面临的风险和机遇

科学的预测通常基于对所研究系统的深入分析，建立数学模型来获得预测结论。系统分析师需认识到，所建立的数学模型未必能正确反映系统发展变化规律，可能得出错误预测结果，因此需要对预测结论进行验证。

## 关键技能要求

- **沟通能力**：能够与关键人员、用户进行有效访谈和沟通，能够设计并实施问卷调查
- **分析能力**：能够理解复杂业务流程，抽象出系统逻辑模型
- **建模能力**：熟练使用数据流图（DFD）、E-R模型、用例模型等建模技术
- **评估能力**：能够综合评价技术、经济、操作等方面的可行性
- **预测能力**：掌握因果分析、类比分析和统计分析方法，能够建立数学模型进行趋势预测
- **文档能力**：能够撰写清晰、专业的可行性研究报告和需求规格说明
- **技术选型能力**：能够根据项目约束和业务需求选择合适的技术架构和方案
- **方案设计能力**：能够设计满足功能和非功能需求的系统解决方案

## 在系统开发生命周期中的位置

系统分析师主要在系统规划与分析阶段发挥作用，其工作为后续的系统设计和系统实施奠定基础。系统分析师需要确保正在解决的问题确实是要求解决的问题，避免后续开发中出现方向性错误。

## 论文写作与考试准备

系统分析师在职业发展中常需参加软考等认证考试，论文写作是关键考核环节。

### 考试时间分配

| 环节 | 建议时间 |
|------|----------|
| 试题选择 | 3分钟 |
| 论文构思 | 12分钟 |
| 写摘要 | 15分钟 |
| 正文撰写 | 80分钟 |
| 检查修改 | 10分钟 |

### 论文结构模板

以「软件需求获取方法及应用」为例，论文结构安排如下：

| 过程 | 字数 | 是否必要 |
|------|------|----------|
| 摘要 | 300~400 | ✓ |
| 项目概要 | 400~600 | ✓ |
| 需求理解重要性 | 100~200 | ✓ |
| 需求获取方法特点 | 800~1200 | ✓ |
| 方法选择依据 | 400~500 | ✓ |
| 应用效果 | 200~300 | ✓ |
| 总结 | 100~200 | ✓ |

### 摘要写作要点

摘要应概括反映正文全貌，引人入胜：

- **模板一**：本文讨论……系统项目的……（论文主题）。该系统……（项目背景、简单功能介绍）。在本文中首先讨论了……（技术、方法、工具、措施、手段），最后……（不足之处/如何改进/特色之处/发展趋势）。在本项目的开发过程中，我担任了……（作者的工作角色）。

- **核心原则**：摘要不是正文的部分，而是正文的抽象。正文不是摘要的延伸，而是摘要的扩展。不要把正文"接"着摘要写。

### 正文写作技巧

1. **以自我为中心**：体现实际经验，不要罗列课本内容；条理性说明实际经验；明确"我"的工作任务和所起的作用；以"我"在项目中的贡献和努力为重点。

2. **站在系统分析师角度**：从全局角度把握问题，关注选择某个方案的原因，而不是专注于某个具体的实现细节。

3. **忠实于论点**：仔细阅读论文试题要求，理解背景说明；根据正确的题意提取论点加以阐述；绝对服从论点，回答试题的问题，就试题的问题进行展开。

4. **条理清晰，开门见山**：列出提纲，简明扼要；不要试图覆盖论文题目的全部内涵，而是将侧重点放在汇报考生自己在项目中所做的与论题相关的工作上。

5. **标新立异，要有主见**：动脑筋写一些个人的见识和体会，让评卷专家有深受启发、耳目一新的感觉。

6. **首尾一致**：做到开头与结尾间互相呼应，术语的意思忌途中变卦，避免论文内部不一致导致阅卷专家产生不信任。

### 常见问题及避免方法

| 问题 | 说明 | 避免方法 |
|------|------|----------|
| 走题 | 按三段论方式写论文，未仔细阅读三个问题 | 认真阅读试题问题，按问题组织内容 |
| 字数不够 | 摘要和正文未达到要求 | 摘要350字以上，正文2500字左右 |
| 深度不够 | 措施太多但都蜻蜓点水 | 选择2~3个特色方法深入展开 |
| 缺乏项目 | 未说明具体项目背景和功能 | 必须具体说明项目名称、背景和功能 |
| 口语化 | 到处都是"我" | 使用"我们"代替部分"我" |
| 段落太长 | 每个自然段超过8行 | 调整段落结构，避免阅卷专家疲劳 |

### 评分标准（满分75分）

| 评分维度 | 权重 | 说明 |
|----------|------|------|
| 切合题意 | 30% | 技术部分、理论部分和实践部分都需切合要点 |
| 应用深度与水平 | 20% | 分为有很强、较强、一般、较差四档 |
| 实践性 | 20% | 从大量实践到初步实践分为四档 |
| 表达能力 | 15% | 逻辑清晰、表达严谨、文字流畅、条理分明 |
| 综合能力与分析能力 | 15% | 分为很强、比较强、一般三档 |

**及格线**：45分；**优良**：60-75分

**扣分项（-5~10分）**：
- 摘要不规范（未写、过于简略、无实质性内容，字数少于120字直接不及格）
- 字迹潦草难以辨认
- 过分自我吹嘘或夸大其词
- 内容有明显错误和漏洞
- 实习性质项目且应用水平较低

**不及格情形**：
- 虚构情节、有严重不真实内容
- 无项目开发实际经验、纯理论
- 内容方法陈旧或项目水准低
- 不切题意、内容空洞
- 正文少于1200字
- 文理不通顺、错别字多、条理不清晰

**加分项（+5~10分）**：
- 独特见解或深入体会
- 符合信息系统发展趋势
- 内容翔实、体会中肯、思路清晰
- 项目难度高、质量优异或涉及国家重大工程
